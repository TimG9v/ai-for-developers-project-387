## Цель

Основной сценарий бронирования проверен на живом приложении в браузере — по
кейсу ручного e2e-тестирования из task-4
(`context/docs/task-4/20260930103108-manual-e2e-test-case.md`, часть B, B1–B9).
`descripton.md`: «Проверьте сквозной сценарий бронирования в браузере».
Расхождение ожидания и поведения фиксируется тикетом, а не правкой кейса
задним числом.

## Предусловия (real-run перед стартом)

1. Шаги 1–5 завершены: тикеты #14–#18 закрыты, `make test && make lint` — exit 0.
2. Приложение запущено:

   ```bash
   make dev
   ```

   backend `127.0.0.1:8081`, frontend — порт из вывода `next dev` (по умолчанию
   3000). Перед прогоном — чистое состояние (перезапуск backend сбрасывает
   in-memory — это и есть B9).
3. Прочитан e2e-кейс B1–B9 (таблица «Часть B») и ADR 0002 (граница ролей:
   owner-операции без авторизации).

## Инструмент (открытый вопрос 1 общего плана)

- Браузерный прогон — инструментами сессии: Playwright MCP / Chrome DevTools
  MCP из `descripton.md`, если подключены; иначе встроенные browser-инструменты
  среды (открыть страницу, прочитать DOM, кликнуть, отправить форму).
- Новую зависимость в репо (`@playwright/test`) не заводить: автотесты сценария
  уже живут на швах (Testing Decisions спеки), браузерный прогон — ручная
  приёмка. Заведение зависимости — только явным решением пользователя.

## Действия

1. Прогнать B1–B9 по порядку, фиксируя фактический результат каждого пункта:

| #  | Роль     | Шаг                                              | Ожидание                               |
| -- | -------- | ------------------------------------------------ | -------------------------------------- |
| B1 | Владелец | создать тип «Звонок», описание, 30 мин           | тип виден в списке                     |
| B2 | Владелец | опубликовать слот на завтра для типа             | слот виден в календаре                 |
| B3 | Гость    | открыть `/booking`, выбрать тип                  | слоты только этого типа, окно 14 дней  |
| B4 | Гость    | выбрать свободный слот, имя + email, подтвердить | запись создана, показано подтверждение |
| B5 | Гость    | повторить запись на тот же слот (другой гость)   | ошибка занятости, 409; тип не важен    |
| B6 | Гость    | попытка записи на слот в прошлом / за окном      | слот недоступен / отклонён валидацией  |
| B7 | Гость    | пустое имя или email                             | форма не пропускает; API тоже (400)    |
| B8 | Владелец | `/admin`: список записей                         | запись B4 с деталями: гость, слот, тип |
| B9 | —        | перезапустить backend, обновить страницы         | данные исчезли — in-memory, ожидаемо   |

2. API-проверки мимо UI — curl по контракту (формы — из `openapi/openapi.yaml`,
   поля camelCase) на :8081; особое внимание B5/B7: правила работают при
   прямом запросе, не только в форме.
3. Каждый пункт: сверка с колонкой «Ожидаемый результат»; скрин/лог факта —
   в отчёт шага.
4. Расхождение → заводится тикет в трекер (метка по `docs/agents/triage-labels.md`)
   с шагами воспроизведения; кейс не правится. Мелкие дефекты текста/вёрстки —
   тоже тикет, не правка на ходу мимо ревью.
5. Остановить dev-процессы:

   ```bash
   make stop
   ```
