## Решение сессии: представление списка встреч (открытый вопрос 3 общего плана)

Контракт отдаёт `GET /bookings` → `Booking[]` (`id`, `slotId`, `guestName`,
`guestEmail`, `createdAt`) — без времени слота и названия типа. Два пути:

- **Рекомендация: join на клиенте** — страница владельца делает три вызова SDK
  (`bookingsList`, `slotsList`, `eventTypesList`) и собирает строки
  «гость + время слота + тип» локально. Контракт не меняется, тикет закрывается
  в рамках текущей спеки.
- **Альтернатива: расширение контракта** — модель встречи владельца
  (гость + время слота + тип одним ответом). Тогда жёсткий порядок: правка
  `contracts/main.tsp` → `make generate` → код обеих сторон; и новый эндпоинт
  фиксируется тестом HTTP-шва.

«Предстоящие» = слоты с `startDateTime` не раньше текущего момента
(фильтрация — по решению сессии: на клиенте при join, на сервере при
расширенном контракте); прошедшие встречи — вне объёма (Out of Scope спеки).

## Действия

1. Пользователь запускает `/implement` с тикетом: «реализуй #18 из спеки #13».
2. TDD на швах:
   - **Backend:** failing-тест — `GET /bookings` возвращает записи всех типов
     (создать через репозиторий записи на слоты разных типов — список содержит
     все), пустое хранилище → `[]`. Ракурс владельца: эндпоинт без авторизации
     (ADR 0002) — охрану не добавлять.
   - **Frontend:** failing-тесты — `/admin` рендерит строки: имя гостя, email,
     время слота, тип встречи (моки SDK: bookings + slots + eventTypes при
     join); пустой список → понятное состояние («Пока нет записей…», на
     русском); занятые слоты календаря при этом не ломаются. Никакого
     рукописного `fetch` — только сгенерированный SDK.
3. Красный → зелёный; `make test && make lint` в конце — exit 0;
   `/code-review` внутри `/implement`; замечания — в issue #18.
4. Закрыть тикет:


5. Убедиться, что граф пуст — все тикеты фронта закрыты:
