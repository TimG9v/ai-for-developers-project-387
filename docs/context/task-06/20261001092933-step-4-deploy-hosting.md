## Действия

### Развилка хостинга

- **Render** (основной): сервис создаётся по Dockerfile из репо; платформа
  сама передаёт `PORT` — приложение уже слушает её (шаги 1–3).
- **Railway** (запасной, если Render требует оплату/недоступен): то же —
  Docker-деплой, `PORT`, публичный домен.
- **Ручной деплой** (оба MCP недоступны): пользователь создаёт сервис в
  дашборде по гайду «Как деплой приложения на Render»; агент готовит
  параметры (ниже) и проводит все проверки ссылки. Платформа не важна
  (descripton): важно, что приложение опубликовано и работает по PORT.

Параметры сервиса (для любого пути):

| Параметр       | Значение                                              |
| -------------- | ----------------------------------------------------- |
| Репозиторий    | `TimG9v/ai-for-developers-project-386`                |
| Ветка          | `task-6` (после merge в шаге 5 переключить на `main`) |
| Runtime        | Docker (автодетект `Dockerfile` в корне)              |
| Порт           | платформа передаёт `PORT` — ничего не настраивать     |
| Health check   | путь `/health` (если платформа спрашивает)            |
| Публичный домен| включён (по умолчанию `*.onrender.com` / `*.up.railway.app`) |

### Порядок

1. Зафиксировать способ деплоя (Render MCP / Railway MCP / ручной) в отчёте
   шага.
2. Создать сервис, привязать репо и ветку `task-6`, включить публичный
   домен, задать health check `/health` (если доступно в MCP).
3. Дождаться успешного деплоя (сборка образа платформой; первая — долгая,
   cargo release). При падении сборки — сверить лог платформы с локальным
   `docker build` шага 3 (единственные допустимые расхождения — теги
   базовых образов, если правились).
4. Получить публичный URL (далее `<URL>`).
5. **Проверки ссылки** (real-run):

   ```bash
   curl -sf <URL>/health                                   # {"status":"ok"}
   curl -sf <URL>/ -o /dev/null -w '%{http_code}\n'        # 200
   curl -sf <URL>/booking -o /dev/null -w '%{http_code}\n' # 200
   curl -sf <URL>/admin -o /dev/null -w '%{http_code}\n'   # 200
   curl -sf -X POST <URL>/api/event-types -H 'content-type: application/json' \
     -d '{"id":"et-live","title":"Живой тип","durationMinutes":30}'       # 2xx
   curl -sf <URL>/api/event-types | grep -q "Живой тип"    # roundtrip
   ```

6. **Браузерный сценарий на публичном URL** (сокращённый B1–B4, B8;
   инструмент — playwright-core во временном каталоге вне репо по практике
   task-5 либо браузерные инструменты сессии):
   - B1: из формы `/admin` создаётся тип встречи — в списке появляется
     (запрос в Network — на `<URL>/api/event-types`, тот же origin, 2xx);
   - B2: публикация слота из формы `/admin` — слот в календаре `/booking`;
   - B4: запись гостя на слот из `/booking` — подтверждение, слот исчезает
     из свободных;
   - B8: `/admin` показывает созданную запись.
   Полный B1–B9 не обязателен: серверные правила (409/400, окно) покрыты
   шовными тестами task-5; цель прогона — живой same-origin путь в проде.
7. **Рестарт-проверка** (если MCP позволяет redeploy): повторный деплой →
   типы/записи обнулились (in-memory — ожидаемое поведение, B9); `/health`
   снова 200.
8. Зафиксировать в отчёте шага: `<URL>`, способ деплоя, результаты всех
   проверок, замечания платформы (лог сборки, лимиты free-плана).
