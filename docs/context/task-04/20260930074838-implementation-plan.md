## Задача

Шаг 4 «Проектирование бронирования» (`context/tmp/task-4/descripton.md`): основная
функциональность проекта — типы встреч, календарь свободных слотов, запись и список
встреч владельца. Решений большинство не принято, поэтому задача проходится **картой
решений**, а не прямым кодингом: `/wayfinder` (карта в трекере) → разбор билетов по
одному за сессию → TypeSpec-контракт → генерации (OpenAPI, клиентский SDK, серверные
артефакты) → одна команда генерации → `/to-spec` (спецификация в трекер) →
`/to-tickets` (тиилеты с зависимостями).

Пункт назначения карты: **утверждённая спецификация приложения, по которой можно
раскладывать тикеты**. Код приложения этим шагом не пишется — только контракт,
генерации и трекер (плюс минимальная проверка, что SDK и серверные типы собираются).

## Механика (real-run 2026-09-30 — чтение SKILL.md)

- `wayfinder` (`disable-model-invocation: true` — запускать командой `/wayfinder`).
  Два режима. «Chart the map»: назвать destination (grilling + domain-modeling),
  снять фронт breadth-first, создать карту (issue с меткой `wayfinder:map`) и билеты
  как дочерние issues, блокировки вторым проходом, research-билеты — субагентами.
  Чартинг ничего не решает. «Work through the map»: ≤1 билет за сессию (кроме
  research), claim назначением до работы, решение записывается комментарием, билет
  закрывается, указатель — в Decisions so far карты; ответ может выпускать новые
  билеты из «Not yet specified» (туман войны). Типы билетов: `research` (AFK),
  `prototype`, `grilling`, `task`; grilling — HITL: агент не отвечает за пользователя.
- `to-spec` (`disable-model-invocation: true`): интервью НЕ проводит, синтезирует
  спецификацию из уже обсуждённого — запускать в сессии, где карта и ответы
  загружены. Перед записью: швы тестирования (seams) предложить и **согласовать с
  пользователем**. Публикация: issue с меткой `ready-for-agent`. Шаблон: Problem
  Statement, Solution, User Stories (длинный нумерованный список), Implementation
  Decisions (без путей и кода), Testing Decisions, Out of Scope.
- `to-tickets` (`disable-model-invocation: true`): вертикальные tracer-bullet тикеты
  (каждый проходит через все слои и проверяем сам), блокировки нативными
  зависимостями, разбор раскладки с пользователем (гранулярность, рёбра), публикация
  в порядке зависимостей с `ready-for-agent`. Parent-спеку не закрывать.
- Трекер — GitHub Issues, все операции через `gh` CLI
  (`docs/agents/issue-tracker.md`): карта — issue с меткой `wayfinder:map`, билеты —
  sub-issues, блокировки — нативные зависимости (API `blocked_by` с database id),
  фронт — открытые дочерние без блокеров и без assignee.

## Критерии приёмки (из descripton.md, чек-лист)

- В трекере есть карта решений; задачи карты закрыты с записанными ответами.
- В трекере есть спецификация: пользовательские истории + решения по тестированию.
- В трекере есть тикеты с объявленными зависимостями.
- В репозитории есть TypeSpec-контракт, покрывающий сценарии владельца и гостя.
- OpenAPI генерируется из TypeSpec; команда генерации описана в репозитории.
- Клиентский SDK генерируется из спецификации; фронтенд им пользуется.
- Серверные артефакты генерируются из спецификации.
- Вся цепочка повторяется одной командой; сгенерированное руками не правится.
