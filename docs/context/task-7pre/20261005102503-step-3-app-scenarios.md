## Цель

Доказать real-run, что слои «интерфейс» и «бэкенд» из описания цикла
работают согласованно на основном пользовательском сценарии: владелец
создаёт тип встречи и публикует слот → гость видит свободные слоты,
выбирает время и оформляет запись → владелец видит предстоящую встречу.
Проверка двухуровневая: HTTP-прогон на production-сборке (curl через
same-origin прокси) и браузерный сценарий (по практике task-5/task-6).

## Действия

### A. HTTP-прогон на production-сборке

- [ ] 1. Поднять оба процесса в production-режиме:

  ```bash
  cd backend && cargo run &
  cd frontend && npm run build && npm run start &
  ```

  Ожидание: backend биндит `127.0.0.1:8081`, Next — `:3000`; `next build`
  проходит без ошибок (force-dynamic страницы не требуют живого backend —
  подтверждено task-6). Дождаться готовности обоих (`curl -s
  http://127.0.0.1:8081/health` и `curl -s -o /dev/null -w '%{http_code}'
  http://127.0.0.1:3000/` дают 200).

- [ ] 2. Страницы через публичный фронт (прокси и SSR):

  ```bash
  for p in / /booking /admin /health; do
    printf '%s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000$p)"
  done
  ```

  Ожидание: все четыре — `200`.

- [ ] 3. Сквозной сценарий по API (браузерный путь = same-origin `/api/*`):

  ```bash
  ET=$(curl -s -X POST http://127.0.0.1:3000/api/event-types \
    -H 'content-type: application/json' \
    -d '{"title":"Intro call","description":"smoke","durationMinutes":30}')
  echo "$ET"; ETID=$(echo "$ET" | jq -r .id)

  START=$(date -u -d '+2 days 10:00' +%Y-%m-%dT%H:%M:%SZ)
  END=$(date -u -d '+2 days 10:30' +%Y-%m-%dT%H:%M:%SZ)
  SL=$(curl -s -X POST http://127.0.0.1:3000/api/slots \
    -H 'content-type: application/json' \
    -d "{\"eventTypeId\":\"$ETID\",\"startDateTime\":\"$START\",\"endDateTime\":\"$END\"}")
  echo "$SL"; SLID=$(echo "$SL" | jq -r .id)

  curl -s http://127.0.0.1:3000/api/slots?eventTypeId=$ETID | jq length   # 1

  BK=$(curl -s -X POST http://127.0.0.1:3000/api/bookings \
    -H 'content-type: application/json' \
    -d "{\"slotId\":\"$SLID\",\"guestName\":\"Smoke\",\"guestEmail\":\"smoke@example.com\"}")
  echo "$BK"

  curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:3000/api/bookings \
    -H 'content-type: application/json' \
    -d "{\"slotId\":\"$SLID\",\"guestName\":\"Second\",\"guestEmail\":\"second@example.com\"}"  # 409

  curl -s http://127.0.0.1:3000/api/upcoming-meetings | jq '.[0].guestName'  # "Smoke"
  ```

  Ожидание: тип создан (200), слот опубликован (200), список свободных
  слотов до брони — 1, бронь создана, повторная бронь — `409`
  (контрактное правило «одна запись на слот»), `upcoming-meetings`
  содержит гостя `Smoke`. Слот исчез из свободных: повторный
  `GET /api/slots?eventTypeId=$ETID` — `0`.

  Слой граничных правил (400): бронь без имени
  (`guestName: ""`) → `400`; слот вне окна 14 дней (+20 дней) → `400`.
  Оба — по одному curl из шага 3 с изменённым телом.
