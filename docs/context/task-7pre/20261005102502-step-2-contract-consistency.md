## Цель

Доказать real-run, что слой контракта из описания цикла («определить, что
именно должно делать приложение, и зафиксировать контракт между клиентом и

перегенерируются бит-в-бит (`make generate` no-diff), а документированная
API-поверхность (README) совпадает с контрактом.

## Действия

- [ ] 1. Перегенерация всего каскада:

  ```bash
  make generate
  ```

  Ожидание: exit 0; в выводе — `@hey-api/openapi-ts` (генерация
  `frontend/src/client`, 4 файла) и `Finished dev profile` от cargo.

- [ ] 2. Ключевая проверка — no-diff:

  ```bash
  git status --porcelain
  ```

  Ожидание: пусто (повторение результата 2026-10-05: дрейфа нет).

  **Если diff есть — протокол разбора (не коммитить молча):**

  - `git diff --stat` — какие слои затронуты (openapi / SDK / типы backend);
  - версии инструментов: `cd contracts && npx tsp --version`,
    `cd frontend && npx openapi-ts --version` (или поле в
    `package-lock.json`), сравнение с дрейфом;
  - `git diff openapi/openapi.json | head -50` — по сути изменений:
    новая функциональность 386 не могла появиться, значит дрейф — в
    версиях генераторов или порядке полей;
  - решение: (а) diff косметический (порядок/форматирование) — коммит
    `chore: regenerate contract artifacts` и продолжение; (б) diff
    меняет схемы/пути — стоп, возврат в Debug: контракт разъехался с
    кодом, цикл не продолжается до разбора.

- [ ] 3. Сверка документированной поверхности с контрактом:

  ```bash
  jq -r '.paths | keys[]' openapi/openapi.json | sort
  ```

  Ожидание — 8 путей, ровно как в API-таблице README (стр. 80–89):
  `/bookings`, `/event-types`, `/event-types/{eventTypeId}` (если есть),
  `/health`, `/slots`, `/upcoming-meetings` — фактический список
  сверяется построчно с README; расхождение → правка README (`docs:`
  коммит) как рассинхрона документации.

- [ ] 4. Сверка кодов ответов README с контрактом:

  ```bash
  jq -r '.paths | to_entries[] | .key as $p | .value | to_entries[] |
    "\(.key) \($p) → \(.value.responses | keys | join(", "))"' \
    openapi/openapi.json
  ```

  Ожидание: `POST /bookings → 200, 400, 404, 409`; `POST /slots → 200,
  400, 404`; `POST /event-types → 200, 400`; GET-ы → `200` — совпадает с
  колонкой «Коды» README. Правила бронирования (окно 14 дней, 409 на
  повтор) проверяются поведенчески в шаге 3 — здесь сверяется только
  декларация контракта.

- [ ] 5. Зафиксировать результат: таблица «Проверка» этого файла
  заполняется фактическими выводами команд (дата, exit-коды, список
  путей). Коммит — только если шаг 2/3/4 что-то изменили.

## Коммит

Обычно отсутствует (верификационный шаг). При дрейфе — один коммит

api table with contract` (рассинхрон доков), выполненный агентом в ветке
`task-7`.
