## Фича 1: отмена и перенос записи

Я записался на звонок и ошибся временем. Отменить или перенести запись
негде: слот остаётся занятым до самой встречи, а связаться со мной по
этой записи никто не может. Владельцу остаётся только ждать гостя на
встречу, который не придёт, и вручную разбираться с памятью сервиса —
данных о записи после перезапуска и так не остаётся.

_Откуда: «Что дальше» → «Дополнительные сценарии: перенос и отмена
бронирований». Подтверждение, что сегодня этого нет: в API-таблице README
только GET/POST — ни отмены, ни переноса._

## Фича 2: рабочие окна расписания вместо ручных слотов

Я владелец календаря. Чтобы открыть приём на неделю, я руками публикую
каждый получасовой слот отдельной формой — это десятки одинаковых
операций, стоит отвлечься, и в расписании дырки. Хочу один раз задать
свои рабочие часы («пн–пт, 10:00–17:00 моего времени») и быть уверенным,
что гость из другого региона видит это время корректно для себя, а не
догадывается, чей это часовой пояс.

_Откуда: «Что дальше» → «Гибкое расписание» (окна по дням недели,
перерывы, исключения) + «Часовые пояса» (хранение зоны владельца)._

## Баг 1: дубликаты сущностей при повторной отправке создания

После повторной отправки формы создания (сбой сети, повтор запроса) тип
встречи появляется в списке дважды: сервис молча принимает обе копии.
Дублей может быть сколько угодно, они неотличимы друг от друга, и
владелец не может понять, на какой из них ссылаются слоты и записи.

_Подтверждено на публичном деплое (real-run 2026-10-05):
два POST `/api/event-types` с одним и тем же идентификатором — оба
отвечают 200, в `GET /api/event-types` появляются две одинаковые записи
«Dup test». То же строение хранения у слотов (code-reading:
`backend/src/infra.rs`, `add` — push без проверки уникальности)._
