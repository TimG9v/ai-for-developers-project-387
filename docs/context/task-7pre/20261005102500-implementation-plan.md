## Задача

`docs/context/tmp/task-7-pre/description.md` описывает проект «Запись на
звонок» (упрощённый Cal.com): полный цикл разработки небольшого
веб-приложения с ИИ как рабочим инструментом — определить поведение,
зафиксировать контракт, собрать интерфейс, реализовать бэкенд, покрыть
основные сценарии тестами, упаковать в Docker-образ и запустить в облаке.
Пользователь видит свободные слоты по 30 минут, выбирает время и оформляет
запись; владелец смотрит список предстоящих встреч. Без авторизации,
кабинетов и внешних календарей.

Особенность этой итерации: код приложения уже перенесён из
`ai-for-developers-project-386` (коммит `d26f4ab`, «chore: copy from…»),
рабочий и зелёный. Цикл проходится как **адаптация и верификация**, а не
переписывание — решение пользователя (2026-10-05). Предыдущая попытка
планирования (`tmp/trash/task-7/`) отклонена: трактовала описание как
«финализацию» с выдуманными требованиями, не входящими в `description.md`.

## Ключевое архитектурное решение

Стратегия «адаптация копии» (подтверждена пользователем 2026-10-05):

- **Каждый слой цикла верифицируется real-run**, а не переписывается:
  контракт — `make generate` должен давать no-diff (консистентность
  контракт ↔ OpenAPI ↔ SDK ↔ серверные типы доказана прогоном 2026-10-05);
  приложение — тесты, линтеры, prod-smoke и браузерный сценарий; образ —
  локальная сборка и прогон по `$PORT`.
- **Деплой — новый сервис Render**, трекающий репозиторий 387: оба
  существующих сервиса workspace `hx-study` (`calendar-zvonok`,
  `ai-for-developers-project-386`) трекают только репозиторий 386
  (real-run list_services 2026-10-05). Render MCP в этой сессии подключён —
  в task-6 его не было, теперь деплой выполняется агентом целиком.
- **Гигиена 386**: бейдж CI, clone-URL и ссылка на issue в README
  переводятся на 387; деплой-секция переписывается под новый URL в шаге 5.
  Исторические контексты `docs/context/task-1..6` не трогаются (история
  работы, решением пользователя — «почистить, историю оставить»).
- **Один контейнер, один публичный порт** наследуется без изменений: Next
  слушает `$PORT`, backend — `127.0.0.1:${BACKEND_PORT:-8081}` внутри
  контейнера, same-origin прокси `/api/*` и `/health` через Next rewrites
  (`frontend/next.config.ts`). Архитектура task-6 подтверждена работающим
  деплоем и здесь не пересматривается.

- Шаги 1–4 — на ветке `task-7`, коммиты Conventional Commits; шаг 5 — PR в
  `main`, мерж, деплой (Render создаётся уже на `main`), README-ссылка.

  заполненная таблица «Проверка» и чистый `git status`. Дефект, найденный
  верификацией, чинится fix-коммитом в том же шаге.
- Шовные тесты не трогаем; новые тесты не вводим — функциональность не
  растёт, проверяются существующие швы (`cargo test`, `vitest`, curl-прогоны,
  браузерный сценарий).
- Браузерные прогоны — по практике task-5/task-6: playwright-core во
  временном каталоге вне репо (`/tmp/opencode/...`) на production-старте
  (`npm run build` + `npm run start`), либо встроенные браузерные
  инструменты сессии.
- Правило контракта: сгенерированное руками не правится, источник правды —
  `contracts/main.tsp`; `make generate` — единственный способ обновить
  артефакты.
- `hexlet-check.yml` не трогать: автопроверка Хекслета сама собирает образ
  по корневому `Dockerfile` — файл является контрактом с автопроверкой.

## Review Focus (что скорее всего укусит)

1. **Дрейф контракта при перегенерации**: локальные версии
   `@typespec/*`, `@hey-api/*`, typify могли уехать от собиравших 386.
   Если `make generate` даст diff — не коммитить молча: сначала разбор
   (что и почему перегенерировалось, сравнение версий), решение фиксации.
   Пин — шаг 2 (таблица «Проверка», пункт no-diff).
2. **Параллельная работа в репо**: 2026-10-05 утром коммиты и правки
   package-lock шли из другой сессии, пока дерево меняло статус. Перед
   каждым шагом — `git pull` + `git status --porcelain` (должно быть
   пусто). Пин — предусловия каждого шага.
3. **`PORT` против `BACKEND_PORT`**: `PORT` читает только Next (публичный
   порт), backend — только `BACKEND_PORT`. Прогон образа с двумя разными
   значениями `PORT` ловит захардкоженный порт. Пин — шаг 4 (два
   docker run).
4. **hexlet-check собирает образ сам** по корневому Dockerfile: перенос
   или переименование `openapi/openapi.json`, `backend/src`, смена пути
   контекста ломает автопроверку. Ничего из этого не делать. Пин — шаг 4
   и зелёный hexlet-check в шаге 5.
5. **Холодный старт и память free-инстанса Render**: после ~15 минут
   простоя первый запрос отвечает десятки секунд; ре-деплой обнуляет
   in-memory данные. Сценарий на публичном URL прогонять одним заходом
   после пробуждения; «пустой список после ре-деплоя» — не дефект.
   Пин — шаг 5 (верификация URL).
6. **Security-пайплайн (cargo/npm audit)**: наследует advisory-базу 386;
   на момент снятия состояния был in_progress. Если упадёт на
   унаследованных уязвимостях — разбор отдельным контекстом, не игнор и
   не маскировка. Пин — шаги 1 и 5 (таблица CI).
7. **README-скриншоты ссылаются на `docs/context/task-6/*.png`** — файлы
   в репо есть, пути репозиторионные (не 386-URL): их оставляем. Проверить
   только, что картинки рендерятся после правок README. Пин — шаг 5.
