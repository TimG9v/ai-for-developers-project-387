## Ключевые факты для плана фикса

Зафиксированы при подготовке плана (`code-reading`):

- Контракт уже содержит нужные коды: `ValidationError` (400) в `slots.create`
  и `reschedule`, `ConflictError` (409) в `bookings.create` — **изменения
  контракта не требуется** (только текст `@doc` у ConflictError при смене
  инварианта).
- Фикстура `bookings.rs::seeded_state`: s1 (et1, 30 мин) и s2 (et2, 60 мин)
  стартуют **одновременно** — существующий тест «409 независимо от типа»
  после фикса придётся переписать: первый же букинг на s2 станет конфликтом.
- HTTP-тесты `slots.rs` используют `Utc::now() + 1d` с произвольными
  секундами — сетка 30 мин потребует хелпер привязки времени в happy-path
  тестах.
- `backend::app()` используется тестом «пустое хранилище → `[]`» —
  demo-seed должен подключаться в `main.rs` (бинарник), а не в `app()`.
- Проверка сетки по `timestamp() % 1800` пропускает суб-секунды
  (10:30:00.500): нужен дополнительный `nanosecond() == 0`.
- Хендлер `reschedule_booking` маппит `Err(_) => 404`: новая ошибка
  «вне сетки» обязана получить явную ветку 400, иначе молча станет 404.
