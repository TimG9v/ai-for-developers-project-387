## Задача

Шаг 6 «Docker и деплой» (`docs/context/tmp/task-6/descripton.md`): приложение
упаковывается в Docker-образ (Dockerfile в корне репозитория — по нему
автопроверка Хекслета собирает образ и запускает приложение), при запуске
контейнера приложение стартует автоматически и отвечает по порту из переменной
окружения `PORT`. Затем — деплой на хостинг через MCP-сервер (Render, запасной
вариант Railway), проверка работающего приложения и добавление публичной
ссылки в репозиторий.

## Ключевое архитектурное решение

Требование descripton.md — один контейнер, один порт из `PORT`. Приложение —
два процесса (backend axum + frontend Next.js), поэтому в контейнере:

- **Публичный вход — Next.js**: слушает `$PORT` (`next start` читает `PORT`
  нативно), отдаёт страницы и проксирует API на backend через Next
  `rewrites`: `/api/:path*` и `/health` → `http://127.0.0.1:8081/:path*`.
- **Backend — внутренний процесс** на `127.0.0.1:${BACKEND_PORT:-8081}`,
  наружу не публикуется.
- **Один origin** для браузера: страницы и `/api/*` идут с одного домена —
  CORS-проблема исчезает по построению. Это же — рекомендуемое в тикете #20
  решение («Next rewrites + тот же origin»), то есть шаг 2 плана закрывает
  #20, без которого деплой неработоспособен: из браузера клиентские вызовы
  SDK ушли бы на недоступный снаружи `:8081`.

Альтернатива (CORS-слой на backend, tower-http) отклонена: она не решает
задачу одного порта — браузер всё равно не достучался бы до внутреннего порта
контейнера снаружи. Прокси нужен в любом случае, CORS-слой стал бы лишним.

## Review Focus (что скорее всего укусит)

1. **Коллизия `PORT` и `BACKEND_PORT`**: `PORT` читает только Next (публичный
   порт), backend — только `BACKEND_PORT` (дефолт 8081). Если backend начнёт
   читать `PORT`, в контейнере оба процесса полезут на один порт и контейнер
   упадёт в цикле. Пин — юнит-тесты шага 1 (дефолт и оверрайд) + прогоны
   `docker run` с разными `PORT` в шаге 3.
2. **Браузерная ветка baseUrl**: `api-config.ts` должен дать браузеру
   относительный `/api` (тот же origin), а серверу — абсолютный `BACKEND_URL`.
   Если браузер получит абсолютный дефолт `:8081` — на публичном домене все
   клиентские формы сломаются (симптом как в #20, но уже с другим кодом).
   Пин — vitest в jsdom (шаг 2) + проверка Network-вкладки в браузерном
   прогоне (шаги 2 и 4).
3. **Rewrites и время разрешения**: Next запекает rewrites при `next build`
   (routes-manifest), поэтому цель прокси — константа `http://127.0.0.1:8081`
   (топология контейнера фиксирована entrypoint'ом). Переменную `BACKEND_URL`
   ждать в rewrites не надо — она используется только SSR-вызовами.
   Пин — шаг 2 (комментарий в коде) и шаг 3 (curl `/api/*` из контейнера).
4. **glibc-совместимость стадий сборки**: бинарник `cargo build --release`
   линкуется с glibc дистрибутива базового образа; rust-билдер и node-runtime
   должны быть одной Debian-ветки (bookworm/trixie). Пин — шаг 3: точные теги
   сверяются при первой сборке, запуск бинарника в рантайм-образе
   (`docker run` + `/health`) — обязательная проверка.
5. **Автостарт и отказоустойчивость контейнера**: entrypoint поднимает оба
   процесса и завершает контейнер при смерти любого — иначе тиxо живёт
   полумёртвый сервис (страницы без API). Пин — шаг 3: `docker stop` шлёт
   SIGTERM, оба процесса завершаются; рестарт контейнера пересоздаёт оба.
6. **In-memory данные**: перезапуск контейнера (или ре-деплой) обнуляет
   типы/слоты/записи — ожидаемое поведение до появления БД (B9 task-5), не
   дефект (шаг 4).
7. **`hexlet-check.yml` не трогать**: автопроверка Хекслета по descripton
   собирает образ сама; зелёный hexlet-check на пуше с Dockerfile — часть
   приёмки (шаг 5).
