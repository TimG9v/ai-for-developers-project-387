**Goal:** дополнить GitHub-процесс триажем: ручной вызов агента из issue
(`/oc explain` → разбор → план исправления), воркфлоу автотриажа на
событии `issues` с заданным `prompt`, живая проверка на новой задаче,
сравнение двух разборов и итоговая постановка «что считается
исправлением» в issue.

**Architecture:** новая инфраструктура процесса, не продуктовый код.
Один новый файл `.github/workflows/opencode-triage.yml`: событие `issues`
с `types: [opened]`, обязательный `prompt` (без него агенту на этом
событии неоткуда взять инструкцию), права `id-token: write` +
`issues: write`. Существующий коммент-воркфлоу `opencode.yml` (task-8)
не изменяется — им же пользуется ручной поток шага 1. Продуктовая
функциональность (backend/frontend) не меняется вообще.

**Tech Stack:** GitHub Actions (`anomalyco/opencode/github@latest`),
модель `zai-coding-plan/glm-5.3-flash` + секрет `ZHIPU_API_KEY`
(рабочая связка task-8), `gh` CLI, планы развития task-7pre как
источник issue.

## Задача

`description.md` (task 9 курса): моделируется командная ситуация —
в репозитории появляется неидеально описанная проблема, агент помогает
превратить её в техническую постановку. Два способа позвать агента:
командой в комментарии (инструкция — текстом рядом с командой, агент
читает весь тред) и автотриажем на событии `issues` (комментария нет,
инструкцию обязан передать `prompt` в воркфлоу; то же для `schedule` и
`workflow_dispatch`; исключение — `pull_request`, где без `prompt`
агент разбирает PR по своим правилам). Результат шага: «issue прошёл
разбор с участием агента, из нечёткого описания получилась рабочая
постановка, а новые задачи разбираются автоматически при создании».

## Ключевые решения

- **Два issue из плана развития task-7pre** (конвенция: пункты плана
  оформляются как issue без изменения сути): issue A = «Фича 1: отмена
  и перенос записи» (ручной поток, шаг 1), issue B = «Фича 2: рабочие
  окна расписания вместо ручных слотов» (автотриаж, шаг 3). Обе —
  жалобы пользователя без готового решения, как требует спека; порядок
  очереди плана развития не меняется (следующая на работу — Фича 1).
- **Отдельный файл `opencode-triage.yml`, не правка `opencode.yml`**:
  другие события, права и запуск; предсуществующие воркфлоу не
  трогаются (конвенция task-8). Имя файла — как в docs-примере.
- **Модель/секрет — путь B из task-8**: `zai-coding-plan/glm-5.3-flash`
  + `ZHIPU_API_KEY` (real-run: прогон 37395173305 `success` 83 c).
  Anthropic-пример из docs в этом репо не работает — AuthError
  (инцидент task-8, diagnosis real-run).
- **`types: [opened]`, не `edited`**: правка описания не перезапускает
  агента (без дублей разборов и лишнего расхода); требование спеки —
  «на новой задаче он отработал», `opened` его покрывает.
- **Права — минимум под триаж**: `id-token: write` (OIDC-обмен) +
  `issues: write` (комментарий в issue). `contents: write` и
  `pull-requests: write` из docs-примера не даём: по docs они нужны,
  только если агент создаёт ветки/PR — триаж только разбирает. Если
  живой прогон упадёт на правах — докоммит одной строки `ci:`.
- **Без анти-спам гейта возраста аккаунта из docs-примера**: гейт
  фильтрует новые аккаунты в публичных репо с внешними авторами;
  здесь единственный автор issue — владелец, гейт всегда `true` —
  мёртвый шаг с лишней точкой отказа. Отклонение от docs-примера
  сознательное.
- **`share: false` в триаже**: ответ триажа без ссылки на shared-сессию
  не содержит `//opencode`, которым самопробуждается коммент-воркфлоу
  (наблюдение task-8). Гипотеза, подтверждается отрицательной
  проверкой шага 3; известный паттерн «лишний прогон fail → skipped»
  задокументирован как не-дефект на случай, если гипотеза неверна.
- **Prompt на русском, гарантированно требующий комментарий** с
  разбором (суть, причина + файлы, путь исправления) — зеркалит
  критерии ручного разбора спеки, чтобы сравнение двух разборов
  (задача 5) было честным. docs-овское «Otherwise, do not comment»
  убрано: иначе живое доказательство «он отработал» нельзя подтвердить
  комментарием.
- **Следующий шаг после explain — план исправления**
  (`/oc propose a fix plan`), не `/oc fix`: спека требует итоговую
  постановку «по которой можно брать задачу в работу», а правка
  (ветка `opencode/*` + PR) в требованиях не названа. Альтернатива
  `/oc fix this` — осознанный выбор пользователя (см. открытые вопросы).
- **Через PR, не прямой push в `main`**: конвенция task-7/8
  (PR + `gh pr merge --merge`); тип коммита — `ci:`.

## Механика

- Шаг 1 — issue A и два вызова агента (без коммитов); шаг 2 — ветка
  `task-9`, файл воркфлоу, PR → `main`, мерж; шаг 3 — issue B
  (автотриаж), отрицательные проверки, сравнение, постановка, приёмка.
- Линейность 1 → 2 → 3: шаг 3 невозможен до мержа шага 2 (событийный
  воркфлоу берётся из дефолтной ветки). Шаг 1 от шага 2 не зависит —
  ручной вызов работает на текущем `main`; порядок «сначала ручной
  поток» следует порядку задач описания.
- Расход: 3 штатных прогона агента (explain, план, триаж) + возможные
  самопробуждения коммент-воркфлоу (падают на perm-гейте до вызова
  модели, наблюдение task-8 — расхода нет).
- `docs/context/tmp/task-9/` — рабочий каталог; финальное место
  контекстов цикла решит пользователь по образцу task-8
  (`docs/context/task-9/`) — в объём шагов не входит.
- Секреты: значение ключа не проходит через чат, логи и файлы
  репозитория (no-secrets-exposure); в отчётах — только маски.
- Cycle-report — отдельный контекст-файл после приёмки (по образцу
  task-8 `20261006054241-cycle-report.md`); шаг 3 готовит для него
  материал (сравнение, номера issue/прогонов, таблица приёмки).

## Review Focus (что скорее всего укусит)

1. **`prompt` забыт или пуст** — на событии `issues` комментария нет,
   действию неоткуда взять инструкцию (docs: «Requires `prompt`
   input»); прогон падает или отрабатывает впустую. Ожидание: файл не
   мержится без непустого `prompt:`. Пин — шаг 2 (grep) и шаг 3
   (живой прогон + комментарий в issue B).
2. **Чужой провайдер из docs-примера** — скопированный `anthropic/…`
   + `ANTHROPIC_API_KEY` даст AuthError (инцидент task-8, real-run).
   Ожидание: только `zai-coding-plan/glm-5.3-flash` + `ZHIPU_API_KEY`.
   Пин — шаг 2 (env/model) и шаг 3 (прогон).
3. **Триаж срабатывает на правку issue** — без `types: [opened]`
   каждая правка описания = новый прогон агента (расход, шум). Пин —
   шаг 2 (grep `types:`) и отрицательная проверка (a) шага 3.
4. **Права / perm-гейт** — триаж-прогон падает после checkout
   («does not have write permissions» — наблюдалось в task-8).
   Автор issue — владелец (write), должен проходить; если нет —
   добавить недостающее разрешение одним `ci:`-коммитом. Пин — шаг 3.
5. **Двойной запуск от одного события** — коммент-воркфлоу не должен
   реагировать на создание issue (event mismatch), триаж — на
   комментарий. Пин — шаг 2 (разбор событий) и шаг 3 (сравнение
   счётчиков прогонов).
6. **Дежурный разбор триажа** — flash-модель может ответить общей
   фразой без файлов; сравнение шага 3 фиксирует точность обоих
   разборов, вывод — в cycle-report. Ожидание: комментарий с
   конкретными файлами; иначе пометить в сравнении.
7. **Грязное дерево перед шагом 2** — коммит воркфлоу должен
   содержать только `.github/workflows/opencode-triage.yml`
   (точечный `git add`). Пин — шаг 2 (предусловие и действие коммита).

## Открытые вопросы

1. **`/oc fix` вместо плана исправления** — если пользователь выберет
   сразу правку: агент заведёт ветку `opencode/*` и PR (доп. прогон,
   дороже); текст шага 1 меняется минимально (команда), приёмка не
   меняется (спека требует разбор и постановку, не PR).
2. **Куда попадает итоговая постановка** — по умолчанию комментарий
   в issue A (тред полнее: разбор + план); альтернатива — правка body
   issue A или обеих. Решение пользователя в шаге 3.
3. **Дневной лимит прогонов агента** — при упоре в лимит повторить
   прогон позже (справка task-8); триаж-прогон обязателен для
   приёмки, шаг 3 не двигать, пока лимит не отпустит.
4. **Финальное место контекстов** — переезд `docs/context/tmp/task-9/`
   → `docs/context/task-9/` по образцу task-8 — решение пользователя
   после приёмки, отдельным `docs:`-коммитом, в шаги не входит.

## Критерии приёмки (description.md, «Требования» + «Результат шага»)

- Существует issue A: жалоба пользователя без готового решения
  (текст «Фичи 1» плана развития, без изменения сути).
- В issue A: команда-комментарий + ответ агента с разбором (причина,
  затронутые части кода, предлагаемый путь) + ответ на запрос плана
  исправления; прогоны `opencode` для обеих команд — `success`.
- `.github/workflows/opencode-triage.yml` замержен в `main`:
  событие `issues`, `types: [opened]`, непустой `prompt`, права
  `id-token: write` + `issues: write`, checkout без persist (grep +
  merge-коммит PR), зарегистрирован `active`.
- Существует issue B: триаж-прогон `success` запустился автоматически
  при создании, комментарий агента-триажа виден в issue B.
- Сравнение двух разборов зафиксировано с выводом «который точнее
  и почему» (материал cycle-report).
- В issue A записана итоговая постановка «что считается
  исправлением» — по ней можно брать задачу в работу.
- Предсуществующие воркфлоу зелёные на `main`; дерево чистое.
