## Задача

Шаг 5 «Реализация» (`context/tmp/task-5/descripton.md`): пять вертикальных
тикетов (#14–#18) из шага task-4 реализуются через `/implement`. Тикеты — граф
с зависимостями; в любой момент есть фронтир — тикеты с закрытыми блокирующими.
`/implement` сам пишет тесты на согласованных швах, гоняет типы и тесты по ходу,
в конце проходит ревью и коммитит; от пользователя — проверка результата и
замечания. После тикетов — сквозной сценарий бронирования в браузере (e2e-кейс
B1–B9 из task-4) и приёмка: замечания ревью разобраны, GitHub Actions зелёный.

## Механика (real-run 2026-09-30 — чтение SKILL.md и трекера)

- `implement` (`disable-model-invocation: true` — запускать командой
  `/implement`): TDD на заранее согласованных швах (`/tdd`); регулярный

  звать не нужно (`descripton.md`: «отдельно вызывать тесты и ревью не нужно»).
- Трекер — GitHub Issues (`docs/agents/issue-tracker.md`): тикет закрывается
  после проверки результата; фронтир = открытые тикеты без незакрытых
  блокирующих (native `blocked_by`).
- Правило контракта: изменения только через TypeSpec → `make generate` → код
  обеих сторон; сгенерированное руками не правится (`descripton.md`, AGENTS.md).
- Швы тестирования (Testing Decisions спеки #13): backend — HTTP-слой axum
  (запросы к роутеру, хранение in-memory); frontend — страницы с моком
  сгенерированного SDK.

## Точка внимания: валидационные 400 в контракте (real-run)

Контракт моделирует ошибки только для `POST /bookings`: 404/409
(`openapi/openapi.yaml:30-32`); в `BookingsCreateErrors` SDK — только 404 и 409.
Тикеты #15/#16/#17 требуют серверного отклонения невалидного ввода (пустое
название, неположительная длительность, слот вне окна, запись без имени/email),
а e2e-кейс B7 ожидает «UI + API 400». В контракте 400 не смоделирован.

Порядок при первом же тикете, которому нужен типизированный 400 (по
`descripton.md`): правка `contracts/main.tsp` (например, `model ValidationError`
с `@statusCode statusCode: 400` для create-операций event-types / slots /
bookings) → `make generate` → код обеих сторон. Решение о форме 400-ответа
принимается в сессии тикета (скорее всего #15) и фиксируется в его issue;
тест — на HTTP-шве.

## Review Focus (что скорее всего укусит)

1. Правила бронирования только в интерфейсе: занятость, окно и обязательность
   полей проверяет сервер (409/404/400); UI лишь не предлагает занятые слоты.
   Прямой запрос в API мимо формы не должен создавать вторую запись на то же
   время (шаг 4, тесты HTTP-шва).
2. Рукописный `fetch` мимо SDK — фронтенд ходит к API только через
   `frontend/src/client` (все шаги; в тестах — мок уровня SDK).
3. Правка сгенерированного руками вместо контракта — только правка
   `contracts/main.tsp` + `make generate` (все шаги; `git diff` не должен
   трогать `frontend/src/client/**` и `backend/src/api.rs` без перегенерации).
4. Ключ уникальности записи — `slotId`, а не пересечение интервалов: правило
   карты #5 «одна Запись на Слот, 409 независимо от типа». Пересечение по
   времени у разных типов — не конфликт (решения нет, в объём не входит) —
   не изобретать в шаге 4.
5. In-memory данные исчезают при перезапуске backend (пункт B9 e2e-кейса) —
   это ожидаемое поведение до появления БД, не дефект (шаг 6).

3. Представление «предстоящих встреч» (шаг 5): текущий контракт отдаёт
   `Booking[]` c `slotId`; детали слота и типа либо собираются на клиенте
   (три вызова SDK + join — без изменения контракта), либо контракт расширяется
   моделью встречи владельца (TypeSpec → generate). Рекомендация: join на
   клиенте; расширение контракта — если сессия решит иначе, то по
   contract-first порядку.
4. Закрытие спеки #13 и карты #12 — на приёмке (шаг 7).
