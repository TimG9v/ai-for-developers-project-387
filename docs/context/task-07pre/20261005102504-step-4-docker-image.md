## Цель

Доказать real-run требование описания: «приложение должно собираться в
Docker-образ и запускаться в контейнере» — образ собирается из корневого
`Dockerfile`, при старте контейнера оба процесса поднимаются
автоматически (супервизор `docker/entrypoint.mjs`), приложение отвечает
по порту из переменной `PORT` (проверка на двух значениях), остановка
чистая. Заодно — репетиция сборки, которую hexlet-check выполняет сам.

## Interfaces

- Consumes: корневой `Dockerfile` (3 стадии: rust:1.98.1-slim-bookworm →
  node:25.2.0-bookworm-slim frontend-builder → node:25.2.0-bookworm-slim
  runtime), `docker/entrypoint.mjs` (PORT → Next 0.0.0.0,
  BACKEND_PORT → backend, fail-fast при смерти любого процесса), сценарий
  curl из шага 3 (переиспользуется со сменой хоста/порта).
- Produces: локальный образ `calendar-387` (не публикуется) — доказательство
  для шага 5 (тот же Dockerfile собирает Render); факт «PORT читается,
  не захардкожен».

## Действия

- [ ] 1. Сборка образа (5–15 минут; lock-файлы в репо — сборка
  воспроизводимая, `cargo build --release --locked` и `npm ci`):

  ```bash
  docker build -t calendar-387 .
  ```

  Ожидание: exit 0. Отдельно посмотреть глазами финальные строки стадий:
  rust-стадия — `Finished release`, frontend-стадия — `npm run build`
  без ошибок. Падение на `COPY openapi/openapi.json` или на генерации
  типов = нарушение консистентности из шага 2 — вернуться туда.

- [ ] 2. Прогон №1 — `PORT=8080`:

  ```bash
  docker run -d --name cal387-a -e PORT=8080 -p 8080:8080 calendar-387
  sleep 8
  for p in / /booking /admin /health; do
    printf '%s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8080$p)"
  done
  ```

  Ожидание: все четыре — `200` (первый запрос может занять пару секунд —
  Next стартует; при отказе смотреть `docker logs cal387-a`, дождаться
  строки готовности и повторить curl).

- [ ] 3. API-сценарий внутри контейнера (сценарий шага 3, действие 3,
  дословно со сменой хоста на `http://127.0.0.1:8080`): тип → слот →
  бронь → повтор 409 → upcoming. Ожидания те же.

- [ ] 4. Прогон №2 — `PORT=9090` (ловит захардкоженный порт):

  ```bash
  docker rm -f cal387-a
  docker run -d --name cal387-b -e PORT=9090 -p 9090:9090 calendar-387
  sleep 8
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9090/health   # 200
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/health   # refusal
  ```

  Ожидание: `200` на 9090, отказ на 8080 — публичный порт берётся
  исключительно из `PORT` (пин Review Focus №3 общего плана).

- [ ] 5. Чистая остановка (супервизор пересылает SIGTERM обоим процессам):

  ```bash
  docker stop cal387-b && docker rm cal387-b
  docker ps -a --filter name=cal387 --format '{{.names}}'
  ```

  Ожидание: `docker stop` завершается без таймаута-kill (exit 0, ~10 s),
  список пуст — контейнеров cal387 не осталось.

- [ ] 6. Данные in-memory: после рестарта контейнера записи обнуляются —
  ожидаемое поведение (до появления БД), не дефект. Проверять не нужно,
  фиксируется как известное ограничение README (уже задокументировано).
